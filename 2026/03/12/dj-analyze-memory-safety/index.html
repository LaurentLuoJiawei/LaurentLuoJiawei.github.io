dj-analyze Memory-Safety Configuration: batch/block/prefetch/streaming & Ray DataContext

Created2026-03-12|Updated2026-03-12
|Post View:

Overview

When running dj-analyze (Data-Juicer's analysis sub-command) on large datasets — especially with Ray as the execution backend — several memory-safety related configuration knobs control how data is loaded, buffered, and processed. This post documents those options across four categories: batch, block, prefetch, and streaming.

1. Batch Configuration

Batch-level options control how many rows are processed together in each worker call. Keeping batch sizes small reduces the peak RSS of each Ray worker.

OptionLayerDescription
--batch_sizeData-Juicer YAML / CLINumber of samples sent to each operator call. Smaller values lower per-worker memory but increase scheduling overhead.
--adaptive_batch_sizeData-Juicer CLI flagWhen enabled, Data-Juicer automatically shrinks batch_size if an OOM is detected and retries. Visible in dj-analyze --help.
DataContext.target_max_block_sizeRay DataContext (Python)Maximum bytes per Ray Dataset block. Indirectly caps the batch size seen inside each map call. Not exposed as a CLI flag; must be set in Python before launching a job.

2. Block (Ray Dataset) Configuration

Ray's Dataset abstraction partitions data into blocks. Each block is held in the object store; tuning block sizes is the primary lever for preventing spill-to-disk or OOM in the Ray object store.

OptionLayerDescription
DataContext.target_max_block_sizeRay DataContextDefault: 512 MiB. Larger values reduce scheduling overhead but increase object-store pressure. Reduce to e.g. 128 * 1024**2 (128 MiB) when processing large text rows.
DataContext.target_min_block_sizeRay DataContextMinimum block size. Very small blocks can cause excessive scheduling noise; usually leave at default.
DataContext.block_splitting_enabledRay DataContextWhen True (default in recent Ray versions), Ray will dynamically split oversized blocks. Disable only if you observe excessive split-overhead.

3. Prefetch Configuration

Prefetching trades extra memory for lower I/O wait time. On memory-constrained machines, reducing prefetch depth is often the fastest way to recover from OOM without changing algorithmic batch sizes.

OptionLayerDescription
DataContext.prefetch_blocksRay DataContextNumber of blocks to prefetch per consumer. Default: 1. Set to 0 to disable prefetching entirely (lowest memory usage).
prefetch_factor in PyTorch DataLoaderDataset / training loopIf Data-Juicer is embedded in a training pipeline, the DataLoader prefetch factor independently buffers batches. Reduce if GPU memory is tight during analysis.

4. Streaming / Lazy Execution Configuration

Ray Datasets can execute in streaming (lazy, pipeline) mode, which avoids materialising the entire dataset in the object store. This is the most impactful memory-safety feature for large datasets.

OptionLayerDescription
use_cache in Data-Juicer YAMLData-Juicer configSet to false to skip Arrow IPC caching of intermediate results. Reduces disk and memory usage for single-pass analysis.
DataContext.execution_options.preserve_orderRay DataContextWhen False (default), Ray can reorder output for better throughput. Keeps pipeline memory lower; only set to True if output order matters.
DataContext.execution_options.resource_limits.object_store_memoryRay DataContextHard cap on bytes the streaming executor may use in the object store. Useful as a safety rail on shared machines.
--np / num_procData-Juicer CLI / YAMLNumber of parallel processes. Fewer workers means fewer concurrent blocks in memory. A quick knob when total RAM is the bottleneck.

5. Troubleshooting

5.1 dj-analyze --help | grep -i batch shows --adaptive_batch_size but not Ray DataContext options

This is expected behaviour. dj-analyze --help only surfaces the flags that Data-Juicer parses directly from its own argument parser. Ray's DataContext is a runtime singleton that must be configured in Python code (or via environment variables) before any ray.data call is made. It is not wired into the CLI argument parser.
